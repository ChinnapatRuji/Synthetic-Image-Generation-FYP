    AI Synthetic Generation of Defect Images

    Synthetic defect image generation to address data scarcity in AI-based manufacturing inspection. Uses a LoRA-tuned diffusion pipeline (Realistic Vision 5.1), with an agentic assistant that automates complex hyperparameter tuning so non-specialist users can produce high-quality defect images.

    02

    Overview

    AI-based visual inspection systems need large, balanced datasets to perform reliably. On a production line, however, the most critical defects are often the rarest. A few examples of a failure mode are not enough to train a robust classifier, and detection accuracy suffers exactly where it matters most.

    This project generates realistic synthetic defect images to fill those gaps. It builds on an existing SDXL-LoRA generation workflow and makes it both better (higher-fidelity, more controllable, validated outputs) and easier to use (an agentic assistant that handles hyperparameter tuning, so engineers on the line do not need deep generative-AI expertise).

    2.1Objectives

    1 · Model optimisation

    Improve on the UROP SDXL-LoRA model; now using Realistic Vision 5.1 with text-to-image and image-to-image generation.

    2 · Dataset review

    Check uploads for sufficiency, duplicates and consistency; turn brief notes into visually specific captions.

    3 · Agent-assisted tuning

    Recommend training settings within a compute budget (AgentHPO: Recommender, Evaluator, Decision agents).

    4 · Improved evaluation

    A YOLO classifier trained on real TE images checks every generated image; pass rate and confidence score each run.

    5 · Downstream validation

    Does the inspection model improve? Real-only vs previous workflow vs agent-optimised, on held-out real defects.

    6 · Reporting

    Per-run experiment report with a keep/reject recommendation, integrated into the AITK web app.

    03

    Background & Prior Work

    A previous UROP team (CDE4301, AY2025/26 Sem 1) compared several generative approaches on TE Connectivity solder-pin welding images and built the AITK toolkit, a guided web app for training and generation. This project starts from their conclusions.

    3.1Model selection

    ApproachOutcomeVerdict
    VAE variants (β-VAE, perceptual + TV loss)Controllable but low-resolution and blurryRejected
    Qwen-Image / Qwen-Image-EditGood quality, but ~100 GB VRAM to trainNot viable locally
    Stable Diffusion 1.5 + LoRAArtifacts, outputs unrelated to defectsRejected
    Stable Diffusion 3.5 Medium + LoRABlurry, indistinct defectsRejected
    SDXL Base 1.0 + LoRAHighest fidelity; only model to improve downstream accuracyAdopted

    Table 1. Generative models evaluated in prior work.

    SDXL then went through two optimisation rounds. Natural-language prompts generated by a local Llama 7B model lowered FID but had mixed effects on accuracy. Training one LoRA per defect class ("individual") beat a single shared model on fidelity, FID and accuracy for clear-cut classes; for example, NG-No Solder accuracy rose from 73% to 93%. Individual training was adopted. The team wrapped the pipeline in the AITK web app: setup → training → generation → output.

LoRA training now runs on Kohya_ss instead of Hugging Face PEFT, and generation uses Hugging Face Diffusers in text-to-image or image-to-image mode, with image-to-image the more reliable of the two so far (Section 06).

    5.3Prompts & captions

    Every caption and prompt follows the same pattern: trigger word + domain + class description. The trigger sldrjnt is kept first (keep_tokens = 1) so the LoRA ties it to this product. The domain is "close-up macro photo of a vertical metal electrode solder joint, dark blurry background".

    ClassDescription used in captions and prompts
    OKaligned vertically stacked electrodes, top and bottom electrode on the same vertical center axis, centered solder joint
    NG-Misalignmisaligned vertically stacked electrodes, top and bottom electrode on different vertical center axes, visible lateral offset at solder joint
    NG-Singlevertically stacked electrodes but only one electrode present, missing opposing electrode at the solder joint
    NG-No soldervertically stacked electrodes with no solder, missing solder material between top and bottom electrode
    NG-Not enough soldervertically stacked electrodes with insufficient solder, too little solder material at the joint between top and bottom electrode

    Table 6. Class descriptions.

    Negative prompt

    horizontal alignment, side-by-side composition, two parallel lines, left and right objects, separate objects, duplicate, deformed, blurry background blobs, text, watermark

    Prompt variations

    Added to vary output: metallic texture and solder shape; lighting direction and exposure; solder appearance and highlights; camera position, magnification and depth of field; oxidation and discolouration.

    6.3Text-to-image vs image-to-image

    Txt2img starts from random noise, so the model must generate everything: electrode and solder geometry, alignment, camera composition, lighting and background. That gives high variety but many chances to be physically wrong, which matters for classes like NG-Misaligned where a small lateral shift separates OK from NG. Img2img starts from a real image and adds controlled noise, keeping camera angle and defect geometry while varying lighting, reflections and solder texture. Because the production camera setup is fixed, maximum diversity may not even be desirable.

    Starting pointRandom noiseReal manufacturing image
    Structural preservationLowHigh

    Needs a reference imageNoYes
    Depends on raw image qualityNoYes

    6.4Results so far

    Txt2img: inconsistent

    Two images generated for NG-Misaligned came out one aligned, one misaligned. The model has not reliably learned the class-defining spatial relationship between the top and bottom electrodes, which may mean insufficient training or difficulty with precise geometry.

    Img2img: structurally consistent

    Good reference images gave realistic variations that kept electrode alignment, camera position and defect geometry. But quality depends on the reference: blur, artifacts or existing defects in a poor raw image are preserved or amplified.

    07

    Agentic Tuning Assistant

    The AITK toolkit lets users set training hyperparameters by hand or accept defaults, but good settings differ by defect class and are hard to judge without generative-AI experience. Industry search methods are also static: someone has to define the search space and iterations. AgentHPO (Agent-Driven Hyperparameter Optimisation) replaces this with three cooperating agents. Each new configuration is conditioned on the results of earlier runs.

    7.1Agents

    Recommender

    Proposes the next LoRA training configuration with Bayesian optimisation (Optuna TPE), balancing exploration and exploitation. Uses dataset metadata, the search space, past trial results and Decision feedback. Needs no GPU and no LLM; it only picks the next experiment.

    Evaluator

    Checks every generated image with a YOLO classifier trained only on real TE images. An image passes if YOLO predicts the intended class with confidence of 0.8 or more. The batch pass rate sets the verdict: Accept, Borderline or Reject (Section 08).

    Decision

    Acts on the verdict and the experiment history: Accept saves the config and images, Borderline triggers EXPLOIT (search near this run), Reject triggers EXPLORE (search elsewhere). It can also TERMINATE when the budget is spent.

    Configuration ValidatorA deterministic validator sits between the Recommender and training. It rejects out-of-range or duplicate settings and enforces the run and GPU-hour budget.
    Design choice: no LLM requiredThe closed loop runs on numbers alone: Optuna TPE proposes, YOLO judges, and fixed rules decide. An LLM could be added later to explain decisions, but nothing depends on one.

    7.5Two-stage evaluation

    Training a LoRA for many configurations is expensive, so tuning and downstream testing are separated.

    1. Stage 1, AgentHPO: about 15–20 trials search for strong image-generation configurations; the top few are retained.
    2. Stage 2, downstream validation: only the retained configurations go through the full inspection-model experiment (Section 08).
    08

    Evaluation

    Generated images are judged on two questions: does each image show the intended defect? (a YOLO classifier trained on real TE images) and do the images help? (downstream inspection performance on held-out real defects).

    8.1YOLO judge

    #StepWhatNote
    1Define classesOK, NG-Single, NG-No solder, NG-Not enough solder, NG-MisalignedOne-line rule per class, confirmed with TE
    2Train the judgeYOLO classifier (size n or s) on real TE images onlyYOLO26 or YOLO11; never trained on synthetic images
    3Check the judgeRecall of at least 90% for every class on held-out real imagesIf not, fix labels or add real images first
    4Score imagesPass if predicted class = intended class and confidence ≥ 0.8Low confidence catches broken images

    Table 12. Setting up and using the YOLO judge.

    Broken imagesA classifier always picks a class, so garbled images are caught by the confidence threshold. If some still get through, a sixth "Invalid" class trained on bad generations can be added.

    8.2Batch metrics & verdict

    Scored once per run and class. The pass rate sets the verdict sent to the Decision agent; images that fail are discarded or set aside for checking.

    MetricTargetTool
    M1Pass rateAccept ≥ 80%; borderline 50–80%; reject < 50%YOLO classifier
    M2Mean confidenceHigher than the previous runYOLO classifier
    M3Downstream gainA separate classifier trained on real + synthetic beats real-only on held-out real imagesA different classifier from the judge (Section 8.3)

    Table 13. Batch metrics. Thresholds are starting values, to be calibrated with TE; M3 is the final proof that the images help.

    Accept

    Pass rate ≥ 80%. Save the config and images.

    Borderline

    Pass rate 50–80%. Exploit nearby settings.

    Reject

    Pass rate < 50%. Explore new settings.

    Known limitationThe YOLO judge does not catch copies of training images or near-identical batches. A near-duplicate check can be added later if needed.

    9.3App UI/UX improvements

    The application (web or desktop) is the main way engineers will use the system, so it needs to be usable without generative-AI expertise.

    Guided, step-by-step workflow

    Clear instructions and explanations at every step, from uploading images to approving results, so first-time users know what to do next.

    Agent assistant in the app

    Surface the agent's recommendations and rationale in plain language, so users can see why a setting was chosen before approving it.

    Clearer results and reports

    Side-by-side real vs generated previews, quality scores at a glance, and one-click keep or reject.

    Usability testing

    Test the app with intended users, such as TE engineers, and refine layout, wording and flow based on their feedback.
